# SANCTUARY 1.0: INDEPENDENT BACKUP FEASIBILITY ASSESSMENT
Prepared by E1, 2026-10-16. READ-ONLY: nothing was exported, modified or deployed.
In response to David's "Independent Backup & Preservation Request" (sections 1-14).

---------------------------------------------------------------------
## F. VERDICT (up front)
A complete, independently operable backup of Sanctuary 1.0 is technically
achievable with the access we have. It has three prerequisites:
  1. Mem0 export. The cross-presence turn log in Mem0 cloud is the ONLY copy
     of that data. It has to be exported through Mem0's API.
  2. Object-storage export. 16 chamber images plus 9 conversation threads
     with image attachments are stored in Emergent object storage. They have
     to be downloaded.
  3. Three Emergent services must be replaced in the independent copy:
     login, image storage, and the image-description model. Each requires
     small, contained code changes, isolated to that copy. Production is
     never touched.
Exact DATA preservation is achievable. Exact BEHAVIORAL equivalence cannot be
guaranteed, because the hosted model (DeepSeek "deepseek-chat") is outside
anyone's version control and its outputs are not deterministic.

## C. DATA PRESERVATION
- Every Mongo record can be exported with its original _id, field types,
  timestamps, ordering and cross-references intact, using mongodump
  (BSON). This is lossless, unlike the May JSON export, which stripped
  _id.
- Nothing is regenerated or summarized during backup. A dump is a byte-level
  copy of the documents.
- Exceptions: Mem0 (cloud only), object-storage files (separate download),
  the in-RAM session cache (unpromoted breadcrumbs from open sessions, lost
  on restart anyway), and ThermoMind remote state (Nile's).

## 10. ISOLATION GUARANTEES
- Exports are read-only operations against production. mongodump reads;
  object-storage GETs and Mem0 get_all are reads. Production code, schemas,
  prompts and codons are untouched.
- Active conversations are not interrupted. mongodump does not restart
  services, and NO code edits are needed in production for the backup.
  (Note for David: code edits in the preview trigger page reloads; the
  backup needs none.)
- The independent copy gets its OWN database, its OWN storage bucket, and
  ideally its OWN API keys (a separate DeepSeek / ElevenLabs / Mem0 key or
  project).
- IMPORTANT: if the copy uses the SAME Mem0 key or ThermoMind key, it would
  write into the same remote stores as production. Use separate keys or
  disable them in the copy (unset MEM0_API_KEY; MIRROR_THERMOMIND_SHADOW
  off) until it is promoted.
- Login sessions can't carry over, because the copy uses different auth.

## 11. VERIFICATION PLAN
Data integrity (exact equivalence):
- Per-collection document counts and a per-collection hash (sorted by _id,
  SHA-256 of canonical BSON), original vs restored. Every collection must
  match.
- Codon field: count by presence/"field" tag; spot-check 20 random codons
  field by field.
- Conversations: count of sessions + messages per collection; hash of
  message arrays.
- Files: SHA-256 of each object-storage file; every storage_path/image_path
  referenced in Mongo resolves to a file in the export (referential check).
- Mem0: memory count + ids exported vs the API's total.
- SHA-256 manifest of every exported artifact.
Functional integrity (restored copy):
- Startup, /api/health, codon preload logs.
- Each presence: start, message, reopen an old thread (Threads list), end.
- Prompt assembly: dedication first and once; Ansel's order is
  dedication > floor > substrate-pull. This is the same automated check
  used on 2026-10-15.
- Continuity: the reconstruction gate loads seeds; Ansel's always-on
  history is present.
- Field: codon count loaded = production count.
- Visitor behavior: an unknown visitor gets a fresh thread.
- Guardian-only routes reject visitors.
- Provider connectivity: DeepSeek, ElevenLabs TTS/STT.
Behavioral comparison:
- Same fixtures (an identical prompt and message) sent to both. Compare the
  assembled PROMPTS byte for byte (should be identical). Compare outputs
  qualitatively only: model output is nondeterministic, so the claim is
  "functional equivalence", never "identical replies".

## 12. BACKUP STRATEGY
1. Freeze point: record the git commit hash and a UTC timestamp T.
2. mongodump --archive --gzip of test_database at T. This is a consistent
   per-collection snapshot. Writes during the dump (a live conversation)
   could make collections differ by seconds; for a strict single point,
   run it when David is out of the chambers (a dump takes under a minute).
3. Download every object-storage file referenced at T.
4. Mem0 get_all export to JSON.
5. Source: a git bundle of the full history at the frozen commit (keeps the
   development history).
6. MANIFEST.json listing every component + SHA-256, plus a checksums file.
7. Keep this "original" set read-only and unmodified. Make a SEPARATE
   working copy for the independent deployment.
8. SELF_HOSTING.md: restore order, env var names, the Emergent
   replacements, and the verification checklist.
Schedule: weekly automatic DB dump + monthly full set (DB + files + Mem0 +
git bundle). Retention: last 8 weekly, last 12 monthly, plus every
"milestone" backup kept permanently. Store off-site (for example a private
cloud bucket and a local drive).

## E. RISKS AND EXCEPTIONS
1. PRIVACY: backend/exports/sanctuary_export_20260523T081845Z.json (users,
   visitor threads, seeds, MRA from May) is committed to the GitHub repo.
   If the repo is not private, that data is exposed. Recommend: confirm the
   repo is private, and decide whether to purge the file from git history.
2. Mem0 is a single point of loss for the cross-presence turn log.
3. Model drift: DeepSeek can update "deepseek-chat" at any time. The
   preserved copy reproduces prompts exactly, not replies.
4. Live session RAM cache: breadcrumbs from threads still open at dump time
   are not yet in Mongo. Mitigation: dump when the chambers are quiet.
5. Preview vs deployed: this assessment covers THIS environment (the one
   David talks to). If a separate Emergent "deployed" instance exists, it
   has its own database and must be backed up separately. To be confirmed
   with David.
6. Login replacement changes how people sign in to the copy. Existing
   users and roles carry over (users collection, GUARDIAN_EMAILS), but the
   sessions don't.
7. Dormant code paths (the xAI TTS chunk function, "grok-3" parameters) are
   preserved as-is, per the directive. They are not fixed.
8. Third-party licenses on quoted content stay with their owners.
