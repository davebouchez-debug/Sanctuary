# Security Investigation — codon-forge unauthenticated-write exposure

**Scope:** READ-ONLY. Production DB + production app logs only. No redeploy/restart/write/config change performed.
**Deployment:** milton-propagate (deployment_id 1ac4c22b-0552-4ae0-b9cb-fc6830f97ebe)
**Active run:** 885fdcce-893f-478e-a8c6-31f41b5d14ca | prod DB: `milton-propagate-test_database` | prod URL: https://milton-propagate.emergent.host | frontend: cloudflare

## Allegation
POST /api/codon-forge/save and /api/codon-forge/extract are guarded only by `deny_guests` (auth.py:107), which blocks role="guest" but passes requests with NO session. /save writes into shared `field_phrases` with fields {source:"codon_forge", source_file, lens, created_at}. Question: has it been abused?

## 1. Database evidence (`field_phrases`, prod DB)
- Total documents: **2097**
- `source == "codon_forge"`: **0**
- Counts by `source` (fully accounts for all 2097):
  - legacy_translation: 1883
  - turn_cessation: 208
  - auto_forge: 6
  - (no "codon_forge" source present at all)
- Documents containing a `source_file` field (any source): **0**
- Documents containing a `lens` field (any source): **0**

Because 0 docs have source=="codon_forge", there are NO created_at values, NO source_file values, and NO lens values to group/report for codon-forge.

**Interpretation:** Doubly conclusive. Not only is there no `codon_forge` source, but `source_file` and `lens` — fields written ONLY by the codon-forge save path — are absent from ALL 2097 documents. No codon-forge save has ever written to this collection, by any client (authenticated or not). A successful write would persist regardless of log retention, so the DB is the authoritative record here.

## 2. Log evidence (production backend, Loki)
- Tooling window cap: since_minutes max = 1440 (**24h**). Current pods date from the 2026-11-08 08:30 redeploy; the tool cannot read backend logs older than ~24h.
- Last 24h, filter `codon-forge|CODON FORGE`: **0 matching lines**.
- Last 24h, filter `/api/codon-forge|Saved|Queued|deny_guests`: **0 matching lines**.
- No `[CODON FORGE] Saved` lines: 0. No `[CODON FORGE] Queued` lines: 0.
- No codon-forge requests observed → no client IPs to count (IP diversity N/A).
- Observed baseline traffic in-window was health probes and /api/health/integrations only.

## 3. Verdict
- **No evidence of writes by unauthenticated clients.** The DB contains zero codon-forge documents and zero documents bearing the codon-forge-only fields (source_file/lens).
- **Log retention window:** backend logs are only inspectable for the last ~24h via available tooling (and only back to the 2026-11-08 redeploy of the current pods). Request-level attempts older than 24h cannot be confirmed or denied from logs. However, any *successful* save would have left a durable DB document, and none exist — so the exposure appears **unexploited to date**.

## Recommended fix (not applied — read-only mandate)
- CODE (E1): Replace the `deny_guests` guard on /api/codon-forge/save and /api/codon-forge/extract with a positive authentication requirement (require a valid session/authenticated user), so requests with no session are rejected (401), not allowed through. Re-deploy after the fix.
