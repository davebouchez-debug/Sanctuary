# RCA — milton-propagate resource-utilization alert (OOM / memory pressure)

**Deployment:** milton-propagate (https://milton-propagate.emergent.host)
**Run:** d3e4bac1-63d5-42a1-97ad-510cc0d60f93 (initial, success, currently active)
**Tier:** Starter (tier_0) — CPU request 50m / limit 250m, **memory request 200Mi / hard limit 512Mi**, 2 replicas, HPA/VPA off.
**Template:** fastapi_react_mongo_shadcn_base_image, arm64, Cloudflare frontend.

## Symptom
Owner got an Emergent "Resource utilization alert": >85% of plan resources 5× in 24h. Plan target is 200 MB; 85% ≈ 170 MB.

## What I verified (evidence)

### 1. The backend WAS OOMKilled (hard proof)
`get_pod_events` on the active run:
- `kill_findings`: pod ...-d9w4t container last terminated **OOMKilled (exit 137) at 2026-11-06T03:38:34Z, restarts=1**.
- Container ran 02:33:18 → 03:38:34, was OOMKilled, restarted once (restart_count=1), and is currently Running/ready.
- This is a true OOMKill (reason=OOMKilled), i.e. the process exceeded the **512Mi hard limit**, not merely exit 137.

### 2. The embedding model alone blows past the 200 MB plan target (measured)
Reproduced in an isolated sandbox on this run's source (`backend/field_memory.py`, fastembed==0.9.1 / onnxruntime==1.31.1 / numpy==2.4.2; model dir `backend/models` is **129 MB** on disk — the `Qdrant/bge-small-en-v1.5-onnx-Q` ONNX weights):

```
bare python3                : 11.9 MB RSS
after import numpy          : 24.6 MB
after import field_memory   : 31.9 MB
after _get_model() load     : 261.5 MB   <-- +230 MB from loading the ONNX model
after one query_embed()     : 263.7 MB
after 4600x384 f32 matrix   : 265.8 MB
```

So a process that does nothing but load the embedding model already sits at **~262 MB RSS** — above the 200 MB plan target (the 85% / 170 MB alert line is crossed with huge margin) and already more than half of the 512Mi hard ceiling. This is **before** the real app is loaded: the ~5,500-line `server.py` plus motor/pymongo, uvicorn, httpx clients, and the many large modules (`ansel_canonical_memory.py` 137 KB, `sanctuary_core.py` 60 KB, the canonical/presence memory modules, etc.) all add on top. The model load is **lazy** (`_get_model()` on first embed), so RSS is modest at boot and then jumps ~230 MB permanently on the first field-memory recall or the first cron embed and never comes back down.

**Answer to "does idle baseline exceed 200 MB?":** At cold boot, no; but after the first embedding use (which happens quickly via the hourly cron / first recall) the resident baseline is ~260 MB+ for the model alone, i.e. permanently above the 200 MB plan target. Combined with the full FastAPI app it approaches/exceeds the 512Mi hard limit, which is what produced the single OOMKill at 03:38.

### 3. Background workload (from app logs, 24h)
- **Hourly cron** `POST /api/observatory/cron/tick` → 202 Accepted at ~:07 each hour; plus an internal "hourly-loop" at ~:38 running 4 ledger versions (v1.0.0–v1.3.0).
- **Constant external polling**: `GET https://api.x.ai/v1/models` 200 OK **every ~2 minutes**, non-stop (a health/keepalive loop — note: this is xAI, not the DeepSeek/ElevenLabs the report suspected).
- Periodic `GET https://thermomind-production.up.railway.app/run?...sanctuary_health_probe` → **401 Unauthorized** (external probe, auth-gated; harmless but noisy).
- Real user traffic present and healthy: `POST /api/tts/speak` 200, `GET /api/health/integrations` 200, DeepSeek `chat/completions` 200, ElevenLabs TTS 200.

### 4. Did user-facing requests fail?
No 5xx anywhere in the 24h log window (status histogram = only 200 and 404). The only 404s are the internal k8s probe hitting `GET /health` (the app exposes `/api/health/integrations`, not `/health`, so the probe always 404s — non-5xx, so it does not fail the readiness/health gate, but the probe path is misconfigured). During the single OOM restart at 03:38 any in-flight requests on that one replica would have dropped, but the second replica stayed up, so there is **no evidence of user-visible failures**.

### Not measurable with available tooling
There is no CPU/memory time-series metric tool here. Exact MB-over-time and CPU% curves could not be read. CPU spikes most plausibly coincide with the ONNX embedding inference (CPU-bound, capped at 250m) and LLM streaming, but this is inferred, not measured. The OOM, the tier ceilings, and the per-process RSS of the model are all directly measured/observed.

## Root cause
The app legitimately needs more than the Starter tier grants. The local fastembed/ONNX embedding model (`BAAI/bge-small-en-v1.5`, loaded in `field_memory.py`) adds ~230 MB RSS the moment it is first used, pushing the Python process to ~260 MB+ on its own — above the 200 MB plan target continuously (driving the repeated >85% alerts) and, together with the full FastAPI app and concurrent embedding/LLM work, past the 512Mi hard limit once, causing the OOMKill (exit 137) at 03:38.

## Fixes
1. **User — raise the tier (Resources tab).** Starter's 512Mi hard limit / 200 MB target is too small for an app that resident-loads a 384-dim ONNX embedding model (~260 MB just for the model + numpy/onnx). Move to a tier with a higher memory limit (e.g. Launch/Grow) to clear the OOM and stop the >85% alerts. Confirmed cause = memory ceiling, OOMKilled observed.
2. **Code (E1) — reduce the memory footprint** so the app fits comfortably: cap onnxruntime threading/arena (e.g. `SessionOptions` intra/inter-op threads = 1, disable the CPU mem arena) to cut arena overhead; avoid holding the full per-presence embedding matrices in the module `_cache` indefinitely; and reconsider the 2-minute `api.x.ai/v1/models` poll and the auth-failing thermomind probe (noise, extra httpx buffers). These lower the baseline but will not by themselves bring a resident ONNX model under 200 MB — tier (1) is the primary fix.
