## Root cause (CODE — identity-source divergence)
There are two different identity sources that are never reconciled on the read path:

1. **Session create / auto-resume** — `presence_template.py` `start_session` calls `chamber_identity(db, request, …)` (user_aliases.py), which for a signed-in guardian reads the **verified session cookie** and returns the authoritative `qa-david`. It ignores any client-supplied user_id. So sessions are correctly keyed to `qa-david`.

2. **Thread sidebar list** — `ThreadSidebar.jsx` calls `GET /api/threads/{presence}?user_id=<useIdentity().userId>`, where `userId` is the **client-side `localStorage.sanctuary_user_id`** (IdentityContext.jsx). `threads.py` `list_threads(presence, user_id)` trusts this client value verbatim and runs `resolve_user_aliases(db, user_id)`.

The verified identity is never enforced on the thread-list query. When the browser's `sanctuary_user_id` holds any value NOT in qa-david's alias set, resolve_user_aliases returns only that lone id and the qa-david sessions don't match → empty/partial sidebar, even though the threads exist.

How the browser ends up with a non-canonical id:
- `IdentityBadge.jsx` "set name" flow: `POST /api/users {name}` → `setIdentity(name, created.data.id)` writes a BRAND-NEW user id into `sanctuary_user_id` — an id never added to the canonical alias set.
- Pre-auth / legacy typed-name ids, or an `ephemeral-…` id, likewise are not in the alias set.
- `IdentityBridge` does write `/auth/me`.user_id (qa-david) into localStorage once AuthContext resolves, but it does not guarantee precedence over a value set by the badge flow or a pre-existing/ephemeral value, and list_threads has no server-side guard regardless.

Note on the "fresh thread": bb5d1ad6's last message is 07:11Z. If David returned >2h later, `find_resumable` correctly starts a fresh thread (expected, 2h rule). The reported bug is specifically the sidebar NOT listing the existing thread, which the divergence above explains.

## (4) Other chambers
Affected the same way. `ThreadSidebar`/`ThreadedChamber` is generic and used by every presence; every chamber's `/start` uses server-verified `chamber_identity` while every chamber's sidebar uses the same client `localStorage` userId. Observed usage in ResonancePod, ClarityPod, MirrorArchive, Playground, etc. So David's thread lists in all chambers share this mismatch whenever the browser's sanctuary_user_id ≠ his verified id/aliases.

## Exact fix
**CODE (E1) — primary, server-authoritative identity on the read path:**
- In `backend/threads.py`, have `list_threads` (and `delete_thread`) derive identity for a signed-in user from the verified session (the same `_user_from_request` / `chamber_identity` the `/start` path uses) instead of trusting the `user_id` query param. Resolve aliases on that verified id. This guarantees the sidebar and the session always agree. Fall back to the supplied user_id only for anonymous/unauthenticated visitors.
- Hardening (frontend): for a signed-in user, the sidebar and the `/start` body should always use the verified `authUser.user_id`, and `IdentityBridge` must take precedence over any `IdentityBadge`/localStorage value (ideally the "set name" badge is disabled/ignored while signed in) so the browser can't carry a non-canonical `sanctuary_user_id`.

**DATA — none required.** The thread exists under `qa-david`, is not deleted, and `qa-david` is already a canonical alias. (A stop-gap of adding the browser's stale id to the alias set would surface the thread but is a workaround, not the fix.)
